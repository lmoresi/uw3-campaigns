# #893 probes: peak memory of a custom-FMG solve with a placed ladder level

Issue #893 reports 10 to 23 GB per rank (170 to 377 GB at np 16) after "Setup solver",
before the first iteration, when the custom-FMG coarse tail holds a placed ribbon level.
These probes did not reproduce it serially; what is left runs only in parallel.

Fixture, both probes: an annulus (radii 0.5 and 1), `refinement=2`, `qdegree=2`.
The finest level is an unsplit placed ladder ribbon (`place_fault_ribbon_2d`,
`mesher="ladder"`, `split=False`, width `2h`, `h = cellSize/4`) on the base. The trace starts at
radius 0.9, polar angle 80°, and runs 0.3 inward at a 35° dip. "placed 1" adds a second placed
ribbon on L1 (width `4h`) to the tail, `[L0, L1, placed(L1)]`; "placed 0" is `[L0, L1]`. The
Stokes problem has no-slip on both walls, forcing `cos 3θ r̂`, tolerance 1e-6, and
`set_custom_fmg(..., field_id=0)`.

- `p_893_memory.py <cellSize> <placed 0|1> [top radius]` runs the whole solve. RES prints
  the largest per-rank peak RSS and the sum over ranks, before and after the solve, with the
  global cell count of each level. Use a fresh process per case.
- `p_893_crosspart.py <cellSize> <fraction> [top radius]` runs the cross-partition node
  builder (`custom_mg._node_transfer_no_repair`, barycentric), serially. It maps the placed
  level's whole P2 node cloud, which every rank gathers, against a fraction of the finest's
  nodes.

`ru_maxrss` is in bytes on macOS and kilobytes on Linux; both probes convert to MB.

## Serial results (macOS, 12-core Apple M4)

These ran on development on 2026-11-20, rechecked on 2026-11-25. Every solve converged
(SNES reason 2) in 3 velocity iterations.

| cell | trace top | finest cells | tail [L0, L1] | tail [L0, L1, placed(L1)] |
|---|---|---|---|---|
| 0.2 | 0.97 | 2,320 | 370 MB | refused: the carve reached the wall in two spans |
| 0.1 | 0.97 | 9,628 | 510 MB | 520 MB (2026-11-20); 528 MB (2026-11-25) |
| 0.025 | 0.9 | 142,594 | 3,044 MB | 3,212 MB (2026-11-20); 3,161 MB (2026-11-25) |

At 0.97 the ribbon outcrops through the outer wall, which the placement handles. At 0.9 it is
interior, 0.1 from the wall. On L1 at cell 0.1 or 0.2 that is about one L1 cell plus the
ribbon's half-width, and the placement refuses it ("the ribbon's cavity reached the domain
wall"). That refusal dates from 2026-08 (#549, #670); it is not new. At cell 0.025 the same
geometry has room, so the reported size uses 0.9. Pass the top radius as the third argument.

The cross-partition builder at cell 0.025, against the placed level's 72,064 coarse P2 nodes:

| fine nodes | nnz | peak growth | time |
|---|---|---|---|
| 17,918 (a sixteenth) | 53,658 | +10 MB | 0.5 s |
| 286,700 (all) | 856,980 | +100 MB | 2.0 s |

Neither grows anywhere near 10 GB. The candidate is in what follows the build: the assembly of
the cross-partition transfer (one MPIAIJ) and PETSc's Galerkin products. A cross-partition
transfer has many off-rank columns, and the non-scalable `MatPtAP` can allocate by the global
column count on every rank.

## The trend run (Linux, MPI)

Run cell 0.025, the reported size, at np 4, 8 and 12, both tails, once with defaults and once
with the scalable product. Each line is a fresh process:

```bash
export OMP_NUM_THREADS=1
for np in 4 8 12; do
  for placed in 0 1; do
    mpirun -n $np python p_893_memory.py 0.025 $placed -memory_view -info :mat \
      > m893_np${np}_p${placed}_default.log 2>&1
    mpirun -n $np python p_893_memory.py 0.025 $placed -memory_view -info :mat \
      -mat_product_algorithm scalable > m893_np${np}_p${placed}_scalable.log 2>&1
  done
done
grep -h "^RES" m893_*.log
```

Command-line PETSc options reach the solve, because underworld3 initialises petsc4py with
`sys.argv`. To confirm which product algorithm ran, read the routine name in each log:

```bash
grep -ho "MatPtAPSymbolic_MPIAIJ_MPIAIJ[A-Za-z_]*" m893_np8_p1_*.log | sort | uniq -c
```

If the default and scalable runs show the same routine, the option did not change the
algorithm and the comparison says nothing about it. The serial runs above use the SeqAIJ
product (`MatPtAPSymbolic_SeqAIJ_SeqAIJ_SparseAxpy`) either way.

What answers #893: does the per-rank peak of "placed 1" grow with np while "placed 0" stays
flat or falls? If it does, does the scalable product remove that growth?
