## Is a solved value refreshed in `mesh.lvec` before another solver reads it? (2026-11-14, development 4b782b21, with #1170)

**Verdict: refreshed. The answers agree.**

**Case.**
- **Mesh and solver 1:** a 2-D simplex box (cellSize 1/16). Stokes solves (v, p) with no slip on all walls, a pressure nullspace and tol 1e-10.
- **Solver 2:** a Poisson solver for T, whose source reads both fields, `1000·v_y + 10·p`.
- **Sequence:** Stokes solves for body force A, then solver 2. Then Stokes solves for body force B, then solver 2 again, so a stale aux vector would carry A's v and p into B.
- **Variants:**
  - creation order, default (V, P, T) or scalar first (T, P, V);
  - with or without an explicit `mesh.update_lvec()` before solver 2;
  - solver 2 built before or after the first Stokes solve.
  - Each at np 1 and np 4.

**Result.**
- **Within a rank count,** all 8 variants give the same ∫T² and ∫T·x after A and after B, to every printed digit (13 at np 1; 12 to 13 at np 4).
- **B never carries A's values:** ∫T² is 2.308e-3 after A and 2.644e-2 after B, in every variant.
- **Across rank counts,** the raw runs differ: ∫T² after A is 2.308079505e-3 at np 1 and 2.292246076e-3 at np 4. That is the pressure gauge: mean p is +1.27e-4 at np 1 and −4.97e-4 at np 4, and `10·p` is in the source.
- **With the mean pressure taken out of the source,** np 1 (default order) and np 4 (scalar first) agree to 11 digits:
  - after A: ∫T² 2.304846709437e-3 and 2.304846709393e-3;
  - after B: 2.644322904938e-2 and 2.644322904935e-2.

**So:** the value a Stokes solve writes reaches the aux vector a second solver reads, in either creation order and without an explicit refresh. There is no missing refresh to report. A coefficient that reads a gauge-free pressure needs the gauge fixed, or the mean removed, to compare across rank counts.

**Scripts and logs** are kept on the review workstation, in `runs/2026-11-14-lvec/` (`lvec_probe.py`, `lvec_gauge.py`, `logs/`).

### #408: boundary_flux 3-D assembly memory

Read: the 3-D branch of `_desmear` (`utilities/boundary_flux.py`) no longer allgathers. It `comm.gather`s the coordinate-keyed reactions and trace elements to rank 0, which assembles and solves, and `scatter`s each rank's values back (commit 732831f1, "Avoid replicated 3D boundary-flux recovery", via #593). - Rank 0 still holds the whole boundary as Python objects.

### Where the other ranks wait
In the plain reproducer the failing rank exits. On its way out, PETSc's garbage
cleanup does an allreduce. That allreduce meets the allreduce the other ranks
are already in, the message sizes differ, and MPICH aborts ("Message
truncated"). So this run aborts instead of hanging.

To see the wait itself, a diagnostic variant catches the error on the empty
rank and sleeps. It ran at np 3. The supervisor then reported a hang (exit

This is the same MPI_LOR, count-1 allreduce named in the abort message above.

### Controls (same script, same build)
- np 1, one cell: exit 0, "integration_points proxy created".
- np 2, no empty rank ("full"; cells [8, 8]): exit 0, created on both ranks.
- np 3, no empty rank ("full"; cells [6, 5, 5]): exit 0, created on all ranks.

### Cause
- The failing call is in
  src/underworld3/discretisation/discretisation_mesh_variables.py,
  `_BaseIntegrationPointVariable._create_petsc_fe`:

      cStart, _ = self.mesh.dm.getHeightStratum(0)
      return create_delta_fe(self.mesh.integration_rule,
                             self.mesh.dm.getCellType(cStart), ...)

- The value goes to src/underworld3/cython/petsc_quadrature_fe.pyx,
  `create_delta_fe`, which calls
  `DMPlexCreateReferenceCell(PETSC_COMM_SELF, polytope, ...)`.
- Why it fails with no cells: on an empty rank the height-0 stratum is empty
  (cStart == cEnd). `getCellType(cStart)` is then asking about a cell that does
  not exist, and it returns DM_POLYTOPE_UNKNOWN. PETSc has no reference cell for
  that type. The cell type is a property of the local plex, and an empty rank
  has none to ask.
- The cell type is the only per-cell input to the element. The quadrature rule
  (`mesh.integration_rule`) is already built from the reconciled
  `mesh.isSimplex`, so it is the same on every rank.
- The collective the others wait in: the ranks with cells finish
  `_setup_ds` and reach the eager `_ = self.data` in
  `_BaseMeshVariable.__init__`. There, `_set_vec` calls `dm.createSubDM`, and
  its DMClone does an MPI_Allreduce (LOR). That is the first collective they
  block in, and the empty rank never arrives. On a mesh that already has fields,
  `_setup_ds` takes its `dm_old.clone()` path, so the wait would probably come
  earlier, in that clone.

### Suggested fix
Get the polytope from information every rank agrees on, not from local cell 0.
Either:
- map (`mesh.dim`, reconciled `mesh.isSimplex`) to TRIANGLE, QUADRILATERAL,
  TETRAHEDRON or HEXAHEDRON; or
- allgather the local first-cell type (populated ranks only), as `Mesh.__init__`
  already does for isSimplex, and use that.

Either way the empty rank builds the same element and enters the same
collectives. After the fix, check that `integration_points`, `data` and
`cell_data` give zero-length arrays on the empty rank. Also check that
`IntegrationPointVariable` created directly, and the DDt and materials callers,
work with an empty rank.

### Other proxy locations
- proxy_location="cells": no problem. Exit 0 at np 2 (cells [0, 1]) and at
  np 3 (cells [8, 8, 0]). It is a plain discontinuous MeshVariable, built with
  `PETSc.FE().createDefault` from `mesh.isSimplex`.
- proxy_location="nodes" (the default): no problem. Exit 0 at np 2 and np 3
  with the empty rank. Same path as "cells".

#   LAYOUT=randN  random assignment, seed N

    dmod = uw.discretisation.discretisation_mesh

        if not isinstance(res, tuple):
            return res

                             for c in range(cS, cE)]) if n else np.zeros(0)
            yn = (ymid - ymid.min()) / max(np.ptp(ymid), 1e-300) if n else ymid

            # c941b: the reverse. Prints the corner's cells and where they went.

                corner_cells = [i for i, v in enumerate(cv) if kc in v]
                fcell = [i for i in corner_cells if sum(abs(X[w, 0] - cx) < 1e-9 for w in cv[i]) >= 2]
                rf, ro = (0, 1) if lay == "c941a" else (1, 0)
                for i in corner_cells:

## Findings

1. Low: a rebuilt history leaves its first set of variables on the mesh. When the setter rebuilds the flux history, the variables of the history it replaces stay registered on the mesh. Saved state carries them too. This happens for `NavierStokesSLCN(order=1)` given an order-2 model, which is the case this PR is for.
   - **Example:** on the 2 → 1 → 2 sequence, the mesh carries the original order-2 history (`psi_star_sl_270_0/1` and its flat copy) and the order-1 one (`psi_star_sl_319_0` and its flat copy). Only the final history is used.
   - **Effect:** harmless to the answer, and a restart rebuilds the same sequence. It costs memory and checkpoint size.
   - **Possible fixes:** build the flux history when the model is set, or after it, instead of in `__init__`. Or drop the replaced history's variables from the mesh.

2. Low: at order 1 with the inclusion, the stress moves slightly away from Stokes while the velocity moves closer. With ETD-1 and a fixed dt, v goes from 1.6e-2 to 1.1e-2 and the level-0 stress from 2.8e-2 to 3.1e-2. With a changing dt, v goes from 4.0e-2 to 1.3e-2 and the stress from 2.8e-2 to 3.0e-2. All of these are at the level of `NavierStokes` against Stokes on the same box (3.3e-3 to 2.6e-2), so I read them as time-discretisation differences between the families, not a defect. The PR body could say that the order-1 stress is not uniformly closer.

3. Low (existed before this PR; separate decision): SLCN's partition spread is set by the commit projection's tolerance. It is about 5e-4 in stress at np 2 and np 3 (table E), against 5e-5 for `NavierStokes`. This PR does not change it, and the #1298 body defers a tighter history-projection default to a separate decision.

4. Low: the cross-version checkpoint break is named in the PR body. Release notes should carry it, since a viscoelastic SLCN run checkpointed on development will continue with a different momentum flux.

The diff was read in full. The `requires_stress_history` branch gives F1 = `constitutive_model.flux` minus pressure plus the penalty term, as in Stokes. The viscous path keeps the Adams-Moulton average: its code is unchanged by this PR, though I did not rerun a viscous-only SLCN probe. Stokes and `NavierStokes` are bit-identical between base and the merge.
